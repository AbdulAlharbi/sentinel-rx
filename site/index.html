Why it matters

Impact at the local level, at the global level, and on the research gap

Incident response is the most expensive, least automated part of running software, and today's auto-remediation is a runbook that cannot tell a symptom from its cause. The agents meant to replace it resolve roughly 11% of realistic incidents on public benchmarks, are never tested against a compromise hiding inside an outage, and are believed when they say “recovered”. Sentinel-RX was built against those three facts.

Locally — sovereign, on-premise, and ready for regulated operators

Everything runs on one machine with an open 7B model served by Ollama: no telemetry, logs or network flows leave the premises, which is the constraint that banks, utilities, telecoms and government services in the Kingdom operate under. Scarce SRE and SOC talent is the binding constraint for Saudi enterprises scaling digital services; an agent that handles the diagnosis and the safe first response, and escalates with a full trace when it cannot verify recovery, multiplies the people who are already there instead of replacing them. The design degrades safely: with a 1.5B model it recovers fewer incidents but still makes 0% false claims and 0 harmful actions, so it stays trustworthy on cheaper hardware.

Globally — the security-blind spot in AIOps

Every published incident-recovery benchmark injects one accidental fault per scenario. Real incidents stack faults, and some “performance problems” are intrusions: a compromised host phoning home looks like a slow service, and an ops agent that restarts it destroys the evidence and re-infects the host. Sentinel-RX detects the beacon hidden among health checks and update polls, enforces contain before restart, and never claims recovery while a beacon attempt remains. Over 27 held-out runs with a live C2 beacon it recovered 100% with zero harmful actions, where a single-shot LLM and a raw-telemetry agent were harmful 0.48 and 1.11 times per run.

On the research gap — five gaps, five measured answers

The accompanying literature review surveys AIOpsLab, ITBench, OpenRCA, RCAEval, RCACopilot, RCAgent, STRATUS, ToolEmu, BAYWATCH and CTU-13 and ends with five gaps. Each one maps to a metric this benchmark reports:

  • G1Concurrent, confounded faults → recovery flat at 100% from 1 to 3 faults; every baseline degrades
  • G2Security hidden inside ops incidents → beacon detector + contain-before-restart, 100% isolated-before-restart
  • G3Verification of recovery → false “recovered” as a headline metric: 0% vs 70% single-shot
  • G4Cost of the agent → 6 103 tokens/incident vs 35 018 for the raw-telemetry twin
  • G5Robustness → 95–100% recovery under 4 perturbations and an unseen fault type

Approach

Detectors compress, the model reasons, the safety layer screens, the verifier decides

Four cheap deterministic detectors turn thousands of metric samples, log lines and network flows into a short ranked evidence list. A local qwen2.5:7b proposes ranked hypotheses and targeted checks, then an ordered plan, two JSON calls per iteration. The safety layer enforces an eight-action allowlist, refuses containment of hosts without beacon evidence, reorders plans so containment precedes restarts, and undoes any action that drops observable health by more than 0.15. The verification gate compares post-action telemetry with the remembered healthy baseline and re-scores known beacon pairs; “recovered” may only be claimed when nothing is flagged, otherwise the loop continues (budget 8) or escalates with the trace.

Security-aware G2

A RandomForest on inter-arrival regularity, spectral concentration, autocorrelation and sub-window stability finds C2 beacons among health checks and update polls; destination knowledge is a prior, not a bypass.

Verified, not believed G3

A contained implant keeps trying; the firewall emits blocked flows, so “contained” and “eradicated” are distinguishable and a false claim is falsifiable. The scorer checks every claim against hidden ground truth.

Robustness, ablations, cost

Each component protects a different metric

Same agent, same prompts, same cache policy, on held-out variants with degraded telemetry, renamed services, an unseen fault type and a smaller model. Then one component removed at a time: without the verification gate the agent takes the same actions but claims success in 80% of runs; without the loop it recovers 20% and escalates honestly; without the beacon detector recovery halves; without the safety layer recovery is unchanged but 0.60 harmful actions per run appear.

The recorded live demo: three faults on five real services

make demo-live starts five real local HTTP services and a C2 sinkhole, injects a memory leak on api, a connection-pool hold on db and a beacon on worker every ≈4 s, and runs the byte-identical agent. Health fell from 1.00 to 0.10. The model's first plan tried to restart worker; the safety layer blocked it because the beacon detector had flagged the host. Verification refused “recovered” twice, naming the live beacon. In the third iteration the model blocked the worker's egress and only then restarted it. Ground truth from the live system afterwards: no active faults, restart-before-containment = 0, final health 1.00.

Verified & not verified

How the numbers were kept honest, and what they do not show

Discipline, in code

  • Split guard. 30 dev scenarios for tuning, 20 held-out with fault combinations and type multisets never seen in dev; the runner refuses non-dev splits without --final and logs every such run with its git revision. The agent was frozen (tag v1-frozen) before the first held-out run.
  • Sanity floors. do_nothing and random are permanent baselines: any scenario they recover is a broken check. They recover 0% on held-out.
  • Scorer audit. Mid-development the recovery metric was challenged; two lenient spots were found (a health formula that let one sick service hide, and uncounted containment of innocent hosts), fixed, and every earlier run re-scored. v0 and v1 turned out not to be harmless; the numbers are kept, labelled, in docs/RESULTS.md.
  • Replay. Every LLM response is cached by content hash; make smoke and CI reproduce the committed numbers with no model installed.

Known gaps, stated at the same confidence

  • The simulator is small and hand-written. Five services, nine known fault types with scripted symptoms that match the taxonomy the agent is told; the unseen fault type is the only open-world test.
  • One seed for the secondary arms. llm_only, perturbations, ablations and the small-model run use one seed (n = 20); their deltas are directional. The 3-seed llm_only pass was stopped twice for time and both attempts are in the run log.
  • Synthetic beacon training data. No real captures; a real deployment would retrain on NetFlow or Zeek data and face evasion.
  • Replay is exact, re-recording is not. Ollama decoding is not bit-stable even at temperature 0, so a fresh recording is a new experiment.
  • Not published yet. The repository, CI run and this site live locally until the author pushes them.

Run it

Clone, replay, then record your own

Python 3.12, no Docker. Replay targets need no model. Recording targets need Ollama at localhost:11434 with qwen2.5:7b.

# install and verify, no LLM needed
$ make setup          # venv, pinned deps, scenarios, beacon detector training (~1 min)
$ make test           # 108 tests
$ make smoke          # 5 dev scenarios from the replay cache (< 60 s); CI adds regression floors

# exact replay of the headline table from the committed cache
$ python -m bench.runner --split heldout --config agent --seeds 3 --final --replay

# with Ollama + qwen2.5:7b
$ make demo-live      # 5 real local processes + 3 concurrent faults + the agent
$ make all-final      # held-out, perturbations, ablations, report (hours)

# this page
$ python -m http.server -d site 8000
