# DESIGN.md — decisions and trade-offs

Sentinel-RX is a security-aware agent that identifies, diagnoses, recovers and *verifies* the
recovery of a failing enterprise system, plus a benchmark that proves it does so on unseen
incidents. This document records every non-obvious decision and the trade-off behind it.
The research motivation (gaps G1–G5) is in `docs/literature_review.pdf`.

## 1. One agent interface, two environments

**Decision.** The agent only ever talks to `env/base.py::Env` (`list_services`, `get_topology`,
`get_status`, `get_metrics`, `get_logs`, `get_flows`, `apply_action`, `undo_action`, `wait`,
`snapshot`, `now`). `SimEnv` (deterministic simulator) and `LiveEnv` (five real local
processes) implement it; the agent and detectors are byte-identical in both.

**Why.** Benchmarks need thousands of cheap, seeded, reproducible episodes; a demo needs a
real system with real memory growth, a real dead process and real periodic HTTP beacons.
Sharing one interface means the live demo is evidence that the benchmark agent is not
over-fitted to simulator artefacts (criterion 2, "same agent on both").

**Trade-off.** Everything not on the interface is invisible to the agent, including the
simulator's fault list. The runner reaches ground truth through `SimEnv.gt_*` methods that
are not part of `Env` (`bench/runner.py::ProbeEnv`).

## 2. Simulator realism choices

* **Discrete time, 10 s ticks, 150-tick episodes, agent starts at tick 90.** Faults start
  between ticks 40 and 65 so the first 30 % of the agent's 900 s window is a clean baseline.
  A full episode builds in ~25 ms (`tests/test_sim.py::test_scenario_builds_fast`).
* **Dependency propagation** (`env/sim/world.py::World.compute_metrics`): latency and error
  rate of a dependency propagate upstream with a 0.7–0.8 attenuation; a down dependency makes
  callers fail. Memory, disk, connection counts and cpu are *intrinsic* and never propagate.
  This is exactly what makes "symptom vs. cause" hard (criterion 4).
* **False-positive pressure in flows.** Health checks every 10 s (perfectly periodic) and update
  polls every 300 s (periodic, external) are always present, so a naive "periodic = beacon"
  rule fires on legitimate traffic.
* **Contained implants stay observable.** After `block_egress` the implant keeps *trying*: the
  firewall emits `blocked=True` flows and an `egress denied` log line. Without this, no verifier
  could distinguish "contained" from "eradicated" and a false "recovered" claim would be
  unfalsifiable. The live services do the same (`env/live/service.py::_beacon_loop`).
* **Restart before containment re-infects.** `faults/security.py::C2Beacon.on_action`: a
  restart without containment counts as harmful (evidence destroyed), re-establishes the
  beacon with a new interval and is recorded as a reinfection. This operationalises gap G2.

## 3. Hybrid design: cheap deterministic detectors + LLM reasoning

**Decision.** Detectors (`agent/detectors/`) run first and produce a *compact ranked evidence
list*; the LLM never sees raw telemetry. Four detectors:

| detector | method | why this and not something fancier |
|---|---|---|
| metric anomaly | robust z-score (median/MAD) of recent vs. baseline per series | no training, works with missing values, scale-free |
| log signature | template extraction (numbers/ids → `<*>`) + new/surging templates weighted by severity | catches the one line that names the fault |
| dependency ranker | discounts propagated symptoms explained by an anomalous dependency; intrinsic anomalies never discounted | the single biggest win over threshold runbooks |
| beacon | per-(src,dst) scale-invariant timing features (IAT CV/MAD, fraction within ±30 % of the median, spectral concentration, autocorrelation, sub-window stability, byte-size CV) + destination knowledge, scored by a RandomForest | timing alone cannot separate a zero-jitter beacon from a health check; destination knowledge (internal / allow-listed / unknown) is a legitimate prior |

**Why hybrid.** The LLM is good at *integrating* heterogeneous evidence and choosing an ordered
plan, bad at scanning 4 000 flow records. The `llm_only` baseline (same loop, raw telemetry
summary instead of detectors) measures this claim directly.

**Beacon detector training.** The RandomForest is trained on a synthetic set generated by
`agent/detectors/beacon_train.py`, which is independent of the simulator's traffic generator
(different code, different distributions, harder negatives such as exponential-backoff retry
loops and short allow-listed Poisson windows). Its precision/recall/AP are reported on a
disjoint synthetic test set and, separately, on the simulator's *dev* scenarios (never heldout).
Allow-listed destinations need p ≥ 0.75 instead of 0.5 — the allow-list is a prior, not a
bypass (a beacon fronted through a trusted CDN is still in the training positives).

## 4. The loop (MAPE-K with a step budget)

Per iteration: observe → `diagnose` LLM call (ranked hypotheses + up to 3 targeted checks) →
run checks deterministically → `plan` LLM call (updated hypotheses + ordered plan) → safety
layer → actions → wait → verify. Two LLM calls per iteration keeps cost low (gap G4);
subsequent iterations receive a compact history of what was done and what verification
still flags, so the model changes strategy instead of repeating itself.

**Strict JSON.** Ollama's JSON mode plus a tiny schema validator (`agent/schema.py`); one
auto-repair call on violation. Hypotheses with unknown services are dropped; unknown types
become `other` (that is how an unseen fault type is reported).

## 5. Safety layer (`agent/safety.py`)

1. **Allowlist** of 8 actions on known services (the env enforces it too).
2. **Evidence gate**: containment (`isolate_host`, `block_egress`) is refused unless there is
   outbound-compromise evidence on that host: a detector beacon finding when the detector runs,
   an open `c2_beacon` hypothesis only when it is off (§8b). The LLM once blocked egress on an
   innocent gateway during development (docs/RESULTS.md).
3. **Contain-before-restart**: plans are reordered so containment comes first; a restart of a
   host with an open beacon hypothesis is blocked until it is contained.
4. **Dry-run** mode logs instead of acting.
5. **Transactional no-regression**: observable health before/after every action; if it drops by
   more than 0.15 the action is undone via `env.undo_action` (containment, rate limits and pool
   scaling are reversible; restarts/rollbacks are not and the record says so). For containment
   actions the target itself is excluded from the health comparison, because taking a
   compromised host offline is the intended effect.

## 6. Verification gate (gap G3)

`EvidenceBuilder` remembers the pre-incident baseline from the first observation. `verify()`
compares only post-action telemetry (after a 20 s transient) against that baseline, runs the
beacon detector on post-action flows, and fails on any `blocked` egress attempt. The agent
may claim "recovered" only when `Evidence.problems()` is empty; otherwise it loops or
escalates with the trace. The scorer then checks the claim against hidden ground truth: a
claim without ground-truth recovery is a *false recovery* and is reported as a headline metric.

The wait before verification is 60 s, or 4.5 × the suspected beacon interval (capped at 240 s)
when a beacon was seen — enough events for the detector to re-score the pair.

## 7. Evaluation discipline

* **Splits.** `scenarios/generate.py`: dev (30: 10/12/8 for 1/2/3 faults), heldout (20: 4/9/7)
  with fault-combination keys disjoint from dev, type-multisets disjoint for multi-fault
  scenarios, and a disjoint seed range. `dns_failure` exists only in `perturbations/unseen_fault`.
  `tests/test_scenarios.py` asserts all of this against the committed YAML.
* **Guard.** `bench/runner.py::guard_heldout` refuses non-dev splits without `--final` and
  appends every held-out run to `results/heldout_runs.log` (committed).
* **Seeds and CIs.** Three seed offsets per held-out scenario for the headline table;
  95 % percentile-bootstrap CIs over (scenario × seed) runs. Perturbations and ablations use
  one seed each to stay inside the laptop time budget (docs/LIMITATIONS.md).
* **Baselines**: `runbook` (static rules; given a naive "unknown egress" rule so it is not
  strawmanned on security), `single_shot`, `llm_only`. **Ablations**: `no_verify`, `no_loop`,
  `no_beacon`, `no_safety`.
* **Reproducibility.** Every LLM call is cached by content hash under `cache/` (committed);
  `--replay` forbids live calls, so `make smoke` and CI run with no LLM installed.
  Re-recording with Ollama can differ slightly (batched decoding is not bit-stable); the cache
  is the artefact that makes the numbers reproducible.

## 8. Live environment (`env/live/`)

Five stdlib `http.server` processes (gateway → api → db(sqlite)/cache; worker → db/cache),
a load generator, a monitor thread (metrics every 2 s, health-check flows), a sinkhole that
plays both the C2 server and the update mirror. Faults are real where safe (heap actually
grows, a process actually `_exit`s, the pool is actually held, periodic HTTP calls actually
happen) and sandboxed where not (disk "full" is a 120 MB quota on a sandbox directory; memory
pressure slows handlers proportionally to leaked bytes instead of swapping the laptop).
Everything is torn down by `atexit` and signal handlers. Restart without containment relaunches
the process *with the implant re-injected* (persistence), mirroring the simulator.

## 8b. Decisions from the mid-development scorer audit

* **Health = 0.5·mean + 0.5·min** of per-service health (`env/base.py::combine_health`). With a
  plain mean, one degraded service among five stayed above the 0.9 bar, so naive baselines could
  *claim* recovery. Ground truth was never affected (it requires every fault resolved), but the
  observable number used by the safety layer and by naive claims had to stop lying.
* **Blocking egress is not free.** api's checkout path calls an external payments API; while its
  egress is blocked the simulator adds 0.3 error rate and an `egress blocked by policy` log line,
  so a wrong containment is visible, the regression check can catch it, and the scorer counts
  containment of an uncompromised host as harmful.
* **A restart after containment is a rebuild**: the clean host rejoins the network (egress
  block lifted, isolation cleared) in both environments. Without this, the correct
  `block_egress → restart_service` sequence on api would leave api degraded forever.
* **Containment needs beacon evidence.** With the detector on, `isolate_host`/`block_egress`
  are allowed only on hosts the beacon detector flagged; with the detector off (ablation,
  llm_only) a `c2_beacon` hypothesis suffices; an inbound attack (credential stuffing) never
  unlocks containment. Before this gate, v0/v1 blocked egress on innocent hosts 0.2–0.3 times
  per run (docs/RESULTS.md).
* **Known beacon pairs cannot hide in short windows.** Verification windows hold few flows, so
  new pairs need a stricter score (p ≥ 0.75 unknown / ≥ 0.95 allow-listed or internal), but a
  pair flagged during the incident fails verification on *any* un-blocked flow. The strict
  threshold alone produced two false "recovered" claims in v2.
* **Effective actions and action precision.** The simulator records whether an action changed
  a fault's state; `unnecessary = applied − effective`, `action_precision = effective / applied`.
* **do_nothing and random are permanent baselines**: a recovery check that either one passes is
  broken. Both score 0–1 % recovered.

## 9. Things we deliberately did not do

* No vector memory / RAG over runbooks: the fault taxonomy fits in ~400 tokens of system prompt.
* No fine-tuning: the point is that a 7B local model plus good evidence beats a bigger raw dump.
* No multi-agent orchestration: one loop, two calls per iteration, inspectable trace.
* No Docker: one of our own build constraints (a fanless laptop); stdlib processes are also faster to boot (~1 s).

and CI error bars. Configurations use a fixed categorical palette (blue=agent, orange=runbook,
